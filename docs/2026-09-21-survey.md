# Zotero × 墨墨背单词竞品调研

2026-10-04 复核。调研范围只包括 **Zotero 与墨墨背单词的联动**。支持欧路、扇贝、Anki、Quizlet 或其他平台的功能只作为竞品背景，不属于本项目目标。

## 功能差异

| 能力 | Hover Translate Eudic 的墨墨路径 | zotero-maimemo-sync | 本项目计划 |
|---|---|---|---|
| 只支持墨墨 | 否，墨墨与欧路、扇贝、本地生词表、Zotero 笔记并列 | 是 | 是，产品边界固定为 Zotero × 墨墨 |
| 取词时直接加入 | 是，翻译弹窗点 `+` | 否，需要先建注释再批量同步 | 是，Zotero 原生选中弹窗点「加入」 |
| 是否先写本地队列 | 未见针对墨墨的持久化队列 | 以注释和批量同步为主 | 是，先本地入队，再后台同步 |
| 词本组织 | 选择墨墨云词本 | 侧栏选择目标云词本 | 所有单词统一进入「Zotero 背诵」 |
| 词形去重 | 公开说明有词形处理，但墨墨客户端代码主要按词本内容去重 | 批量追加时去重 | 按词形还原后的原形去重 |
| 学习计划 | 未见 `study/add_words` 联动 | 未见学习计划联动 | 默认加入学习计划，可关闭 |
| 断网、重试、部分成功 | 通用弹窗反馈和请求限流；未见本项目级队列状态 | 批量同步失败提示；没有本项目的逐条状态模型 | `queued / partial / synced / failed`，按步骤恢复 |
| 例句与翻译 | 有翻译、注释和本地例句等通用能力 | 同步注释文本 | 明确不做例句、原文和整句翻译 |
| 其他平台 | 支持多个平台 | 不支持 | 不考虑其他单词软件 |

## 对本项目的结论

现有方案已经覆盖了两种常见入口：

1. **翻译弹窗加词**：操作快，但墨墨只是多平台出口，功能和数据模型受通用插件限制。
2. **注释批量同步**：适合整理已有批注，但操作链长，需要先建注释、选词本、选同步模式。

本项目的差异集中在一条更窄的链路：**Zotero 阅读时选一个词 → 本地可靠入队 → 写入墨墨云词本 → 可选加入学习计划**。它不再以例句、全文扫描、阅读时在背词提示或多平台适配作为差异点。

## 可借鉴的代码结构

两款插件的代码都说明了墨墨接口适配层应该独立出来，但不能直接复制实现。两者均为 AGPL 项目，本项目只借鉴模块边界和可验证的设计思路。

- `zotero-hover-translate-eudic` 将墨墨 HTTP 请求、频率限制、token 失效处理、云词本读写集中在 `src/modules/maimemo.ts`，上层只调用 `getCategories`、`addWord` 等语义方法。这种“API 客户端 + 业务适配器”的边界适合本项目。
- `zotero-maimemo-sync` 将 `src/api`、`src/modules/notepads`、侧栏 `tabpanel` 和偏好设置分开，追加与覆盖通过 `UpdateMode` 区分。这个拆分适合借鉴；本项目明确不提供覆盖模式，因此只保留增量追加。
- 两者都把云词本内容当作一整段 `content` 读取后再更新。这个接口事实必须在适配器中处理，不能让 Zotero 弹窗或队列直接拼接 HTTP payload。

检查后的风险也纳入本项目设计：Hover Translate 的词本缓存是内存级的，重启后不能恢复队列；zotero-maimemo-sync 的覆盖模式可能替换用户已有内容；两者都没有本项目需要的逐条 `queued / partial / synced / failed` 状态和学习计划步骤。因此本项目采用独立的本地存储、同步服务、墨墨客户端和两个网关，而不是沿用它们的同步流程。

## 已排除的竞品方向

LexiNote、zotero-vocab-builder、Zot2Anki 等本地生词本或导出工具可以说明 Zotero 的一般取词交互，但它们不是墨墨联动方案。本项目不把它们的导出平台、复习卡片或本地词库列入需求比较。

同理，Bob 的墨墨插件属于 macOS 划词工具，不是 Zotero 插件；本项目仅将其视为墨墨 API 使用背景，不复制其平台交互。

## 仍需验证的竞争性差异

- `study/add_words` 是否能稳定加入学习计划，以及重复加入时的返回结果。
- 云词本更新是否必须整体提交 `content`，以及并发更新时如何避免覆盖用户内容。
- 墨墨原形归一化与未收录词的实际处理方式。
- Zotero 目标版本中 `renderTextSelectionPopup` 的兼容性。
